## 限额与迁移

普通导入的单文件上限为 10 MiB 与目标库 `MAX_CANDIDATE_BYTES` 的较小值。备份还原使用目标库的 `MAX_CANDIDATE_BYTES`，默认 25 MiB。服务端在建立清单及读取 multipart 前按数据库中的批次用途选择同一规则，multipart 信封另允许最多 16 KiB。相同客户端键和清单可以重放，变更用途返回 409。ZIP 的原文件总量与条数限制继续适用。

Alembic `20261118_0007` 从 `20261117_0006` 升级，将既有批次标为普通导入。旧清单摘要、回执和状态保留。升级前因普通导入上限遭拒的旧还原项保留原状态，从备份清单重新发起还原会创建新的还原批次。

## PR #10 补修验收

保留 Alembic `20261118_0007` 和便携 ZIP `original_zip` v1。普通批次及 `e015921` 已创建的还原批次继续按旧条目摘要精确重放。新还原批次绑定版本化摘要，覆盖用途、排序后的条目及备份清单最小字段。缺少清单绑定的新请求和条目不一致的请求均在写入前拒绝。已绑定批次删去或更改合法绑定会返回 409。

两个隔离 PostgreSQL 和正式 Chrome 网页分别使用 25 MiB 源库、10 MiB 目标库。混合批创建时大项为 `rejected/file_too_large`，小项从 `waiting` 到 `imported`。大项未发送 PUT，也未提交元数据。逐项清单显示大项「超过目标库单文件上限」、小项「已还原」。全超限另跑一批，PUT 和元数据请求均为零。注入一次上传 HTTP 413 也出现同样的逐项文案，浏览器回归同时覆盖该批其他项成功的情况。

把同一目标库提高到 25 MiB 后，用同一 ZIP 再次还原。大项成功，小项为 `duplicate` 并保留原 `asset_id`。两个标题和手动标签均恢复。源原字节、ZIP 解包字节和目标下载字节逐一相等。
