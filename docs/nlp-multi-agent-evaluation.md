# 中文表情包检索需要多代理吗？

**建议先把中文别名和截图中能核对的文字接入现有查询规划器。多代理值得试验的环节是联网搜索遇到歧义后的第二次决策。** 例如用户说“哈吉米”，图库写作“哈基米”。把两种拼写一并查找的成本很低。真正需要判断的是，第一轮搜出的都是同角色的其他动作时，第二轮该保留哪段字幕、换哪个词，还是已经没有值得追的线索。

### 仓库里的证据

对 2026-11-28 下载的萌芽图库固定版本，合并 `gifs.json` 和 `stills.json`，在去重后 2,603 个文件的 `title` 字段逐项做字面子串匹配。“哈吉米”匹配 0 个，“哈基米”3 个，“奶龙”6 个，后两组都是静图。“美团”“黄色袋鼠”“袋鼠”各匹配 0 个。标题主要由上游分类与文件名组成。这次计数测的是元数据用词。它可以解释用户输入与目录词的落差，不能预测网页搜索命中或断言画面中没有袋鼠。专题补充库应单列。[固定语料来源](https://github.com/shumengya/meme-api/tree/d452126069915ee401a125227081cb7ba7ece4b3/public/meme) · [语料准备程序](../scripts/prepare_chinese_meme_corpus.py)

现有网页流程已让视觉模型提取画面、动作和文字，可选择核验实体，再由 DeepSeek 从多个角度生成 2–5 条查询。所有步骤共享查询与搜索预算。候选下载、动画解码、CLIP 排序和版本核对均在下游。两个带站点提示的地球 GIF 成功作业分别耗时 138 秒和 169 秒。更早的六次尝试中，一次内部故障，另五次达到查询上限后仍未找回原件。只看“原件未出现”无法区分漏搜来源、页面提取失败和排名靠后，先按任务记录定位再选择待优化的步骤。[查询规划](../services/search_agent/meme_deepseek.py) · [核验与召回](../services/search_agent/meme_pipeline.py) · [六次尝试](evidence/gif-acquisition/hkgai-web-offline-20261128.json) · [端到端耗时](../submissions/week13/final-technical-brief.md)

### 三个例子怎么处理

| 用户线索 | 可尝试的检索动作 | 判定版本时要核对 |
| --- | --- | --- |
| “哈吉米” | 有文字输入时保留原词，另查“哈基米”。画面可见内容或清晰字幕各保留一项作为约束。仅有一张猫图时，角色名保留为假设。 | 同一只猫的不同动作、同动作的不同字幕。 |
| “奶龙” | 用户明确给出名字时检索名字加可见动作，同时保留一条原字幕查询。只有黄色角色轮廓时另走描述查询。 | 避免选到其他黄色角色、同角色的另一版，或用单帧预览冒充动态原件。 |
| “美团的黄色袋鼠” | 用户明确说出品牌时保留“美团”。从纯图推断时优先采用可辨认的标志、服装和字幕。第二步可以核对候选来源对角色的说明。 | 角色、品牌归属与素材版本分开核对。社区重绘、玩偶照片和表情包可能同时出现。 |

### 一个可检验的最小实验

先固定一份每张截图的可见文字、动作和外观描述。保留用户实际给过的提示，资料库分类、下载站、文件名和答案哈希只交给评分程序。建议用开发集先调试 12 个不同素材家族，再用至少 30 个独立家族做首次配对留出，纳入其他中文梗及只有外观线索的案例。补充的三类热门主题单独展示。若两组同时测试公开网页，按家族交替执行顺序、尽量使用同一时段，并留存首轮失败及完整下载清单。[项目评测协议](retrieval-benchmark-at-scale.md)

| 条件 | 两轮查询决策 | 能观察什么 |
| --- | --- | --- |
| 基线 | 当前单规划器生成多角度查询。另测加冻结别名表的同一流程。 | 先量出拼写归一化本身的贡献。 |
| 同预算单代理 | 同一规划器首轮按输入查询，随后读取首轮标题、已发现媒体和失败原因，选择一次补搜或停止。 | 增益是否主要来自看见真实的搜索反馈。 |
| 同预算双代理 | 第一角色专做别名与视觉线索检索。第二角色只接收原始证据、第一轮实际结果及剩余预算，独立检查身份和字幕冲突，自主选择补搜词或停止。 | 角色与上下文分工能否比同一个规划器的第二轮更有效。 |

两条件均可用同一底层模型。固定流水线里分别提示“生成别名”“提取字幕”属于多提示工作流。这里的双代理条件让第二角色根据检索反馈自行选择下一动作。每次决策记录看到的线索、调用和停止原因即可。文本检索研究给出了 LLM 查询扩展的实验依据，多代理研究也记录了角色协调和任务核验失败。中文动图同版本找回仍需本项目自己的对照结果。[Query2doc](https://aclanthology.org/2023.emnlp-main.585/) · [工作流与代理的区别](https://www.anthropic.com/research/building-effective-agents) · [多代理失败分析](https://arxiv.org/abs/2503.13657)

**实验预算。** 配对条件复用相同视觉输出和既有别名表，固定同一模型版本、检索供应商、候选抽取、CLIP 排序和并发。两轮合计最多 2 次文本模型调用、5 次搜索、60 次原媒体获取。实体求证、重试也占同一额度。开发阶段冻结两组相同的输入、输出 token 总上限、作业超时和单题费用上限。任一耗尽就停止。两组都给核验和抓取留出同样的预算。记录实际输入／输出 token、成功与失败调用、首个可用原件耗时以及实际账单。不能从调用次数推定相同成本，供应商未返回的用量记作未知。以上为拟议实验配置。

**决策口径。** 主指标是已知目标的原件 SHA-256 在下载候选前 3 名中的命中数／全部题数。另报已发现正确原件但排名靠后的数目、同动作不同编码经盲评确认的数目、错版数、按家族配对的净增命中、总费用及 P50/P95 耗时。预算退出和超时留在分母。建议仅在预先冻结的留出集上、双代理对同预算单代理有稳定的跨家族增益，且符合预先确定的成本与延迟上限时才扩大试用。若收益只来自别名表、某一个家族或更多调用，继续用相应的简单方案。若主要损失发生在抓取或排序，将改进工作放回该环节。

这里研究的是推理时如何选择查询与分配已有调用。强化学习需要另行定义可学习的策略、可靠奖励和独立验证集。当前的哈希评分与 Label Studio 盲评分可以积累将来的离线证据。本次没有训练策略，也没有执行付费多代理试验。
