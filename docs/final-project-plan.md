# MemeRetrieve 后半程方向与四人任务

确定日期：2026-11-06；分工更新：2026-11-09。负责人：Jiongle He。本文固定中期之后的项目方向、四人主责和交接标准；后续开发以本文为准。首轮采用相对工作日排期，具体课程截止时间由 Jiongle 核对正式作业后补充。

**项目方向**

MemeRetrieve 继续解决“从一张截图找回原始动态表情”的问题。最终工作流固定为：截图输入、本地 GIF 检索、用户主动继续联网、验证并审阅外网候选、确认收藏、后续本地复用。联网搜索用于补充库外结果，项目的主要成功标准仍是找回用户要的真实动画文件。

第一版使用网页，面向单人或受控小组演示，每次处理一张已裁剪截图。本地结果不合适时，用户点击“继续联网搜索”并补充一句画面描述。自动生成截图描述、自动触发联网和新增来源，排在真实闭环与效果验证之后。静态模板编辑保留为已有实验能力，不占本轮核心开发时间；原生 iOS、微信集成、多用户账户、模型训练和专用向量数据库不列入期末核心交付。

```text
截图 → API 持久化请求与任务 → worker 本地多帧检索 → 审阅候选
  → 用户继续联网并补充描述 → 新建关联任务 → 查询规划与外部搜索
  → 下载、动画验证、去重和视觉重排 → 最多三个候选
  → 用户确认 → 持久保存 → 后台更新多帧索引 → 下次本地找回
```

中期基础是 W07 的 PostgreSQL、独立 worker、CLIP 和 12 个 GIF。现有 [meme agent v1](meme-agent-v1.md) 是独立 SQLite 原型，默认搜索热门静态模板；截图只用于本地检索。后半程复用其查询规划与媒体验证代码，接入 W07 的持久化任务体系。本文中的接口扩展、联网动画找回和收藏索引更新属于待完成工作。

**首轮固定的接口边界**

以下是目标契约。Haoxuan 在第一个工作日给出 API 示例，Jiongle 与 YuanJian 给出 agent 和候选处理函数的输入输出示例。实现如需调整字段，由相关调用方一起更新本文件及示例。

| 边界 | 固定约定 |
| --- | --- |
| 前端 → 创建截图请求 | 沿用 `POST /search-requests` 和现有幂等上传；先创建本地检索任务 |
| 前端 → 继续联网 | 新增 `POST /search-requests/{request_id}/web-search`，传 `description`、`client_search_key`；持久化后返回 `202` 和新 `job_id`。这是新任务，失败重试仍走独立 retry 语义 |
| 前端 → 查询进度 | 沿用请求查询并补充当前 `job_id`、`job_kind`、`stage`，同时返回 `local_job_id` 及关联联网任务列表（每项至少含 `job_id`、`job_kind`、`status`），供刷新后恢复各轮结果；状态沿用 `pending/running/completed/failed`，通过各 job 的候选接口读取结果；正常无候选与执行失败分开 |
| worker → agent | Jiongle 提供 `search_web(image_path, description, work_dir, budget)`；编排搜索及候选处理，返回候选、版本与执行记录。模块不直接写正式业务数据库 |
| agent → 候选处理模块 | YuanJian 提供 `prepare_candidates(image_path, sources, work_dir, budget)`；输入带 provider、标题、来源页面及媒体 URL 的搜索结果，输出已验证并重排的候选、逐项失败原因及本次下载消耗。文件只写入指定临时目录，遵守剩余下载数量及截止时间 |
| agent → worker | Jiongle 汇总每轮结果，使用 YuanJian 的去重与排序逻辑选出最多三个候选；每项包含临时相对路径、SHA-256、来源页面及媒体 URL、provider、格式、帧数和相似度。worker 校验后分配候选 ID，并将结果与执行记录持久化，服务器路径不返回浏览器 |
| 前端 → 确认与收藏 | 现有 review 记录用户决定；新增幂等 `POST /candidates/{candidate_id}/save`，传 `client_save_key`，返回 `asset_id`、`save_status`、`index_status`；候选查询可读取后续状态，重复保存返回同一资产 |
| 后端 → 索引模块 | 收藏保存后，后端持久记录待索引工作，调用 YuanJian 的多帧建索引模块；小库首版采用后台重建及原子切换，确保目录、索引与数据库版本一致 |

外网候选在用户确认前进入临时存储，不能直接冒充固定库中的 `ReferenceAsset`。Haoxuan 扩展候选与资产关联，保留真实来源和帧数。用户审阅、文件保存、索引就绪分别记录；索引失败时保留已保存资产，允许重试，并继续使用上一份可用索引。索引 ready 后，新请求应能查询到新收藏。

搜索首版设为最多两轮；每轮最多一次模型规划和一次搜索调用，整个任务最多下载六个不同媒体地址，返回最多三个候选。整个任务共享一份剩余预算，第二轮和内部模块不得重置额度；相同地址复用已有处理结果。Jiongle 负责跨轮次预算、补搜与停止及执行记录；YuanJian 的候选处理模块遵守剩余下载数量和截止时间，并回报下载消耗；Haoxuan 将总时限和各调用超时写入配置并负责 worker 层中断及失败处理。第一个工作日共同冻结具体时限。执行记录保存查询、调用次数、阶段耗时和失败原因，凭据不进入记录。这里的次数是工程上限，耗时效果由实验测量。

GIF 找回候选必须实际解码且包含多帧；相关静态图或同款替代不计入原 GIF 找回成功。无候选时明确结束；供应商、下载或模型失败应保留原因。来源需要允许项目采用的访问和保存方式，由 Jiongle 记录搜索来源依据，YuanJian 记录媒体获取与保存依据；临时候选清理由 Haoxuan 负责，已收藏资产单独管理。

**效果评估与最终验收**

连续收集真实截图需求后，再标注库内目标、库外且有独立目标证据、目标未知三类，分别报告。开发集和最终验收集按底层 GIF 或梗图家族隔离；同一 GIF 的抽帧、缩放副本只能用于链路检查，不能当独立泛化证据。评估开始前冻结样本、预算和判分；未知目标单列，不能当作已知无匹配。

对照固定为 A“仅本地检索”、B“本地加用户描述直接搜索”、C“本地加查询规划及最多一次补搜”。B、C 使用相同来源、搜索调用预算和候选下载上限；B 的补搜规则在评估前固定，两组实际调用数分别报告，结论针对流程整体的质量与成本，不单独归因为查询规划。首次发现评估使用相同的初始库与缓存条件；收藏后的再次复用单独测量。记录 Top-3 原 GIF 命中、实际动画可用率、确认保存及再次命中、端到端耗时分布、外部调用数与失败类别。同款替代单列。质量和性能门槛在首轮测量后、最终验收集揭晓前由 Jiongle 冻结；不预填未经测量的准确率。

| 最终场景 | 必须具备的证据 |
| --- | --- |
| 库内截图找回 | 真实多帧 GIF 预览、用户审阅与下载，能关联到持久任务 |
| 库外截图首次找回 | 搜索记录、来源、实际解码的动画文件、用户确认结果 |
| 收藏后再次本地命中 | 保存和索引状态、重启后数据仍在、联网关闭时再次检索命中；这项单独算复用验证 |
| 无结果或来源失败 | 正常无匹配与执行错误分开；调用在预算内结束，用户能看到原因和后续操作 |
| 重复操作和中断 | 相同幂等键的重复上传/保存返回原结果，资产按内容哈希去重；主动新建或明确重试按接口创建新任务；中断可见且可重试，索引失败不丢失已保存文件 |
| 可复现交付 | 另一位成员按文档启动真实 API、数据库、worker 和检索，复现完整流程 |
